# Conditional archival of a sealed Google history source

Development foundation, 2026-10-28 JST. This continues [root-resolution fences](NEO_CLOUD_ROOT_RESOLUTION.md), [exact-ID updates](NEO_CLOUD_IDENTITY_UPDATES.md) and [handoff proofs](NEO_CLOUD_HANDOFF_PROOFS.md). No ordinary application action invokes this service. It does not elect, freeze, seal, acknowledge or activate roots, replace local data/bindings or delete objects.

`CloudHistoryArchive` accepts an already sealed source, its confirmed revision, a provider-verified account scope and a durable frozen coordinator intent. It reads the coordinator by exact ID before doing anything to the source, requiring monotonic control state and matching account/epoch/target/session/nonce. It checks the same coordinator again before returning. Unknown, missing, replaced or regressed records fail safely; other coordinator intents may advance without losing this source's intent.

Source reads always use the explicit physical ID and expected name. The complete source body must equal the known canonical sealed bytes. The service first checks its deterministic archived name, allowing restart after a committed-but-unconfirmed rename. If the source still has its original name, both body and confirmed revision must match before one conditional Google v2 metadata PATCH. A source writer/metadata change invalidates the old ETag instead of being silently rebased. IDs, histories, pending intended payload names, uploaded revisions, provenance and reservations remain in the same unchanged source body.

After that one PATCH, the service confirms exact archived identity/name/body/revision and rereads the coordinator. An uncertain response triggers a read of that exact archived ID, never a repeated rename, name lookup or replacement selection. A committed rename can finish through verification; an uncommitted/error outcome stops, and a later fresh invocation can inspect durable state. Cancellation and account/scope changes stop pending work. Rejected authorization does not trigger further file requests. Completion returns verified coordinator/control and archived-source revisions for a **separate** future acknowledgement CAS; no acknowledgement or local checkpoint is written here.

The transport primitive `archiveGoogleHistory()` admits only development history root names and exact IDs/revisions; callers must validate a source's seal and coordinator intent before invoking it. Existing pristine-root and schema 2 initialization recovery paths are unchanged. Dropbox has no revision-conditioned move endpoint; its source-retention/migration flow remains a separate design, not an emulated conditional rename.

The developer-only native probe gains a marked synthetic archive mode. It accepts only a fresh history epoch whose control records contain the synthetic legacy fingerprint derived from that epoch. It receives credentials through anonymous stdin, verifies the supplied source hash and invokes the actual native service; it cannot create or delete fixtures. The external live driver must verify account identity, create only fresh owned IDs and audit all earlier objects afterward. No production root may be used as a probe fixture.
